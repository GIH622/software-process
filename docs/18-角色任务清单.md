### T-2 ⬜ 给「需求定稿那一刻」贴标签 `baseline-req-v1.0`

**先解释这个词**

`baseline-req-v1.0` 拆开是：`baseline`＝基线（这一阶段定下来不再随便动的版本）、`req`＝requirement（需求）、`v1.0`＝第 1 版。合起来就是「需求基线 第 1 版」。

**这个名字是任务书规定的，不能改**：

> 任务书 5.2 命名规范 5）：需求基线 tag 命名：`baseline-req-v1.0`（评审通过冻结）、`baseline-req-v1.1`（变更后更新），旧版本 tag 保留不删除。
>
> 任务书 7.2 第 4）条：GitHub 标签页面可见两个基线版本，**作为需求管理过程的佐证**。

**"贴标签"是什么**：给代码的某一个时间点起个名字。可以理解成游戏存档的档名，或者论文"初稿V1.0"那个另存。它**不产生新文件、不复制代码、不改任何东西**，只是加一条记录：「这个名字 → 指向这次提交」。

- **人话**：给"需求评审通过、文档冻结那一刻"的代码贴个名牌，名字就叫 `baseline-req-v1.0`。
- **为什么老师要**：软件工程课考的是过程证据。有标签才能证明"需求确实在某天冻结了，之后的改动都走变更流程"；没标签就只是一句话。这也是验收第 13 项的依据。
- **什么时候打**：需求评审通过、SRS 冻结之后。**没评审就提前打，等于伪造过程记录。**
- **打完什么样**：打开 `https://github.com/GIH622/software-process/tags` 会多一行名字 + 说明 + 日期，没有其他变化。
- **怎么做**：手册第 9 节（网页：`Releases` → `Draft a new release` → 输入名字 → Target 选 `main` → Publish）
- **判据**：Tags 页面能看到 `baseline-req-v1.0`。

## 五之二、组长 + 开发工程师共同 —— 1 项

### T-17 ⬜ 处理 GitHub 贡献者里的「claude」

- **现象**：仓库 Contributors 列表里有 4 个人：`fengkun001 袁跃宝`、`GIH622`、`claude Claude`、`gjyovo`，其中 `claude` 不是组员。
- **原因**：主线上有 **8 个提交**（2026-10-22，作者均为袁跃宝）在提交信息里带了下面这行，是 AI 编码工具自动加的署名牌：

  ```
  Co-Authored-By: Claude Sonnet 4.6 <noreply@anthropic.com>
  ```

  GitHub 会把共同作者也算作贡献者，所以列表里多出个 `claude Claude`。可用命令核查：
  `git log origin/main --grep='Co-Authored-By: Claude' --format='%h %an %s'`（主线 56 个提交里有 8 个带此标记）

- **影响**：验收第 14 项要求「每人独立、真实的提交记录」。Contributors 里出现 AI 助手，老师可能追问"这些代码是人写的还是 AI 写的"。
- **建议做法**（不要改历史）：
  1. **不要用 rebase 改写已合并的提交**——会让所有 SHA 变化、全组必须重新拉取，风险大于收益；
  2. 在 `README.md` 的「小组协作」一节补一句说明，例如：*本项目部分提交使用 AI 辅助编码工具（提交信息中的 Co-Authored-By 标记即为该工具自动添加），所有代码均由成员本人设计、审查与测试验证*；
  3. 之后提交不要再带该标记（在工具设置里关闭共同作者署名）。
- **判据**：README 里有该说明；此后新提交不再出现 `Co-Authored-By: Claude`。
- **归属**：组长（定口径与文档）+ 袁跃宝（其提交带标记，需调整工具设置）。
